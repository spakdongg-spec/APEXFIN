## 一、问题陈述

### 谁，在什么场景，遇到什么痛点

个人量化研究者 / 小团队量化工程师，每天需要跑一条固定的研究流水线：拉数据 → 清洗入库 → 算指标 → 出结论 → 看板复盘。

这条流水线从「一个 fetch 脚本」开始，三个月后长成几十个互相依赖的脚本。这时会同时爆发四个问题：

**痛点 1：静默失效（Silent Failure）——最致命**

数据源挂了但脚本没报错，管道继续跑，看板照常渲染，结论照常输出，只是底下的数字是三天前的。

> 调研证据（dredyson.com，量化基础设施故障复盘）："Silent failures are the most dangerous failures. Build monitoring that detects **absence of expected behavior**, not just presence of errors. If you only check for exceptions and crashes, you're catching maybe 30% of actual failures."
>
> 同一作者的第一人称记录："I spent six months backtesting strategies on a broken pipeline. The strategies looked profitable in historical tests. They failed miserably in live trading. The root cause was a subscription switch that broke my data feed **without throwing a single error**."

现有解法为什么不行：backtrader / vectorbt 这类回测框架假设「喂进来的数据是对的」，它们没有、也不打算有数据新鲜度概念。Airflow 有 SLA miss 回调，但它只知道「任务没按时跑完」，不知道「任务跑完了但拉回来的是陈数据」——这是两件事。

**痛点 2：管道无限膨胀，没有删除依据**

每加一个想法就加一个步骤，没人敢删，因为不知道哪个下游在读。半年后每日跑 60+ 步，跑 40 分钟，其中 30 分钟在算没人看的东西。

现有解法为什么不行：Airflow/Dagster/Prefect 能画出 DAG 依赖，但依赖图只回答「谁调用谁」，不回答「这一步是否值得每天跑」。后者需要的是**业务重要性分级**，编排器不提供这个语义。

**痛点 3：结论无对账，观点可以永远不错**

今天写「看多，因为 A」，三天后行情反着走，改口写「看空，因为 B」，没有任何机制记录「你三天前说了 A」。研究者对自己的判断质量没有可测量的反馈。

现有解法为什么不行：整个开源量化生态里，回测框架对账的是「策略的历史收益」，没有任何主流框架对账「研究者本人写下的观点」。仅有的相关实现是零散的一次性工具（如 GitHub 上的 `fluencer-predict-track` 用于复盘财经博主历史预测、`backtest-lie-detector` 用于检验回测统计谎言），都不是可复用的框架组件。

**痛点 4：工程骨架每次从零重建**

GitHub 上「个人量化数据平台」类仓库大量存在（solo-quant、Quant-Research-Lab、zer0share、quant-project-template、quant-research-platform 等），但绝大多数停留在「拉数据 + 算因子 + 回测」三件套，且多为单人短期项目，commit 数常在个位到二十之间。

> 调研证据（CSDN 开发者自述，用 Tushare + AI 手搓本地数据同步系统）：作者在第一版做完 review 时才发现"系统里没有保留所有基础信息"，并总结"交易日历不是一个可有可无的附属功能，而应该是整个数据同步系统的**起点**"——一个有经验的工程师，在个人项目里重新踩了一遍基础设施的坑。

这说明：**这个领域缺的不是又一个库，是一份「别人已经踩完坑的目录结构和纪律」**。

### 用户说的 vs 用户真正要的

| 用户表述 | 表面需求 | 真实需求 |
|---------|---------|---------|
| "把可复用工程骨架抽出来做开源" | 代码搬运 | 把「私有系统里最有普适价值的那部分工程判断」固化成可被他人复用的形态 |
| "目的不是让这个项目能运作起来" | 不要做太完整 | 不承诺长期维护责任，但要求**架构表达的完整性**——它要经得起别人读代码 |
| "选最小可跑 Demo" | 功能少一点 | 要一个**可验证的存在性证明**：这套治理机制不是 PPT，是能跑出结果的 |

**这里存在一个需要向上澄清的张力**：用户同时要求「不必运作」和「最小可跑」。这两句话不矛盾，但指向一个明确的产品形态判断——见第七章战略结论。

## 二、目标用户

### 主要用户画像 P1：孤狼量化工程师

| 维度 | 描述 |
|------|------|
| 身份 | 个人量化研究者 / 小团队（1-3 人）量化工程师 / 有交易的软件工程师 |
| 年龄 | 28-45 |
| 技术水平 | Python 熟练，会写 SQL，能读懂 Docker，不一定会前端 |
| 场景 | 每天固定时间跑一次研究流水线，产出当日的判断与看板，长期迭代 |
| 现状 | 已有一套自己攒的脚本，能跑，但正在或即将陷入痛点 1-4 |
| 核心诉求 | 不是「教我做量化」，是「**告诉我这堆脚本该怎么组织才不会烂**」 |
| 会不会 fork | 会。他们的典型行为是 clone 下来读三十分钟，抄走目录结构和治理模块，然后接自己的数据源 |
| 不会做什么 | 不会原样使用你的 Yahoo/FRED 采集器（他们有自己的付费源），不会用你的玩具动量策略 |

**关键洞察：P1 用户 fork 走的是「骨架 + 治理」，扔掉的是「数据源 + 策略」。** 这直接决定了项目的价值密度应该集中在哪里——治理层必须做到能独立被抄走，采集层和决策层只需可替换。

### 次要用户画像 P2：金融/数据方向的求职者与转岗者

| 维度 | 描述 |
|------|------|
| 身份 | 数据工程师、后端工程师，想转金融科技；或量化岗求职者 |
| 诉求 | 需要一个能写进简历、能在面试里讲三十分钟的项目 |
| 痛点 | GitHub 上金融类项目 95% 是 Jupyter Notebook，没有 manifest、质量门、CI、契约这些「生产味」的东西，讲不出工程深度 |
| 使用方式 | 通读代码 + 复现 demo，学分层与治理范式；可能会基于它改造成自己的作品 |

### 次要用户画像 P3：教学者与技术内容创作者

| 维度 | 描述 |
|------|------|
| 身份 | 写量化/数据工程教程的人、课程作者、技术博主 |
| 诉求 | 需要一个「完整但不庞大」的参考系统做讲解素材——Qlib 太大讲不动，一个 notebook 又太薄 |
| 价值 | 这类用户是开源项目最高效的传播杠杆，一篇文章的引流远超自然搜索 |

### 明确不是目标用户

- 寻找现成盈利策略的散户（本项目不含任何真实 alpha）
- 需要实盘下单的交易者（本项目不接券商）
- 机构量化团队（他们有内部平台，不会用个人项目）

**从最后一行读出的产品信号**：`machine-learning-for-trading` 有 2 万 star 但只有 2 个开放 issue。因为它被定位为**配套参考实现**而不是**框架**，用户不会对它提功能请求，也不期待 API 稳定性。这是一个单人维护者能承受的开源形态，与 Airflow（1,791 issue）、Dagster（2,611 issue）形成鲜明对比。这条证据直接支撑第七章的战略结论。

### 竞品分析结论：三个真实空白

1. **「数据新鲜」的定义空白。** 编排器看「任务时间」，dbt 看「写入时间」，没有一个工具看「**业务时间**」。金融数据的唯一正确新鲜度定义是「最新一条记录的 `event_time` 距今几个交易日」，这需要交易日历语义，通用工具给不了。

2. **「质量检查 → 阻断决策」的闭环空白。** Great Expectations / Soda 输出的是报告，报告需要人看。金融研究流水线需要的是**闸门**：数据不达标，决策层拒绝产出，看板显式变红，而不是照常输出一个看不出问题的数字。

3. **「观点对账」的整体空白。** 全网无主流实现。回测对账策略，没人对账研究者本人。

## 四、我们的差异化

### 定位一句话

> **APEXFIN 是一套「不会静默骗你」的金融数据工程参考架构——从采集到看板的每一步都带诚实性约束：数据不新鲜就 fail-loud 停机，管道每一步都要说明自己为什么值得每天跑，每一个结论都被写进对账台账等待被证伪。**

### 对 team-lead 初步判断的验证结论

team-lead 的原始判断：

> APEXFIN = 金融数据工程管道框架，填补「Airflow 太通用、Qlib 太重、backtrader 只管回测」之间的空白，核心卖点是数据治理与诚实性机制。

**判定：核心内容成立，但「框架」这个词必须换掉。**

成立的部分（有证据）：
- 空白真实存在 —— 见上节三个空白，逐条有竞品事实支撑。
- 治理层确实是最独特的资产 —— 已实测确认 APEXDATA 的 `pipeline_manifest.yaml` 对 98 个步骤做了四档 tier 分级（risk_essential 24 / support 27 / display_only 27 / research 20），`check_quality.py` 实现了 6 类检查（freshness / completeness / duplicates / bronze-silver consistency / series continuity / value reasonableness），`audit_freshness.py`、`falsification_monitor.py`、`accountability_ledger.py`、`text_factor_freshness.py` 均真实存在。这不是概念，是跑了一年的实现。

需要推翻/修正的部分：
- **不能叫「框架」。** 框架意味着 API 稳定性承诺、issue 响应承诺、版本兼容承诺。对照证据：Airflow 1,791 个开放 issue、Dagster 2,611 个——这是「框架」这个词的真实成本。而用户明确说「目的不是让这个项目能运作起来」。承诺框架 = 给自己挖坑，且必然烂尾，烂尾的开源项目对个人品牌是负资产。
- **正确的词是「参考架构 / 参考实现」（Reference Architecture / Reference Implementation）。** 对照证据：`machine-learning-for-trading` 20,228 star / 2 个开放 issue。同样量级的关注度，维护负担相差三个数量级，区别只在于用户对它的期待类型。

### 差异化对照表

| 维度 | Qlib | Airflow | dbt | backtrader | **APEXFIN** |
|------|------|---------|-----|-----------|-------------|
| 定位 | AI 投研平台 | 通用编排 | SQL 转换 | 回测库 | **金融数据工程参考架构** |
| 数据新鲜度概念 | 无 | 任务时间 | 写入时间 | 无 | **业务时间 + 交易日历** |
| 质量检查是否阻断下游 | 无检查 | 无 | 是（test 可 fail build） | 无 | **是，且降级到看板可见** |
| 管道瘦身依据 | 无 | 依赖图（不含重要性） | 无 | 无 | **tier 四档分级 + keep_daily** |
| 观点对账 | 无 | 无 | 无 | 无 | **有** |
| 上手成本 | 高 | 高 | 中 | 低 | **目标：5 分钟** |
| 外部依赖 | 数据包 + GPU 可选 | Scheduler+DB+Web | 数据仓库 | 无 | **零外部服务，SQLite，demo 离线可跑** |
| 依赖重量 | pandas + LightGBM 等重依赖 | 大量 | 需数据仓库驱动 | 中 | **8 个顶层依赖，无 pandas** |
| 维护承诺 | 微软团队 | Apache 基金会 | dbt Labs | 已停更 | **明示：参考实现，不承诺 API 稳定** |

**新增差异化维度：无 pandas（v1.1，来自架构决策 ADR-008）**

架构师实测评估后排除 pandas（连带排除依赖它的 yfinance、exchange_calendars，自建约 430 行替代）。理由是 pandas 约 60 MB 体积 + 0.6–1.2 秒冷启动，直接吃掉「5 分钟上手」与「60 秒跑完」两条 P0 指标的大半，而 MVP 实际计算（拉 JSON、写库、算收益率、算滞后交易日）用标准库完全覆盖。

**这条对本项目有正面产品价值，应写进 README 差异化章节**：竞品分析中已记录的 Qlib 用户吐槽——「LightGBM/pandas 版本破坏过工作流，需仔细锁版本」——是重依赖框架的典型代价。APEXFIN 从根上不暴露这个面。对目标用户 P1（孤狼工程师）而言，「clone 下来不会跟我现有环境打架」是极具体的吸引力，比任何架构辞藻都实在。

### 为什么用户选我们（三种用户三个理由）

- P1 孤狼工程师：**因为你已经踩过我正在踩的坑，你的目录结构和治理模块我可以直接抄。** 我不需要你的策略，我需要你的纪律。
- P2 求职者：**因为这是 GitHub 上少数能讲出「工程判断」而不只是「技术栈」的金融项目。** manifest 分级这类东西，面试官会追问，而追问就是加分。
- P3 教学者：**因为它完整但不庞大**，一篇长文能讲完，读者能跑起来。

- Effort = 人日折算（1 = 半天，2 = 1 天，3 = 2 天，4 = 3 天，5 = 1 周）

## 六、MVP 范围

### MVP 必须包含（P0，共 9 项）

F15 配置 / F1 调度器 / F2 采集适配器（fixture + Yahoo + FRED）/ F3 Medallion 分层 / F4 质量门 / F5 新鲜度闸门 / F10 决策抽象 + 玩具动量 / F7 静态看板 / F6 一键 Demo 与故障注入 / F8 README 与架构图

对应用户原始要求的「采集 → 银层 → 质量门 → 决策 → 静态 HTML 看板」端到端最小链路，且额外强制加入 **F6 故障注入演示**——理由见下。

### Demo 数据策略：默认 fixture，真实源为进阶路径（v1.1 修订）

**背景冲突**（架构师高见远提出，2026-08-02）：AC-1 要求「无 API key、5 分钟跑通、结果可复现」，与 F2 内置真实数据源冲突——FRED 强制要 key；Yahoo 虽免 key 但需联网、有限流，且 CI 中跑真实抓取会使「可复现」失效（今天与明天的行情不同，CI 断言无法写死）。

**裁决：采纳架构师方案。**

| 路径 | 数据来源 | 用途 |
|------|---------|------|
| `make demo`（默认） | 内置 fixture pack（committed 小样本 JSON，每源 ≤ 200 条，总计 < 1 MB） | 完全离线、零 key、确定性可复现；CI 验证走此路径 |
| `apexfin collect --source yahoo`（进阶） | 真实网络采集 | 证明适配器接口对接真实源可用；不进 demo 默认链路，不进 CI 断言 |

**产品侧判断：这不是妥协，是正确解。**
1. 治理机制的演示与数据真假无关——闸门拦的是「陈旧」这个状态，不是「真实行情」。
2. 「demo 不联网」本身是卖点：CI 绿灯即证明真正零配置，而不是「在维护者机器上能跑」。
3. 确定性是 NFR 中的 P0 项，真实源与它不可兼得。

**由此产生的 README 硬约束（诚实性红线）**：首屏两张对比截图使用的是 fixture 数据，**图注必须显式标注这一点**。本项目主张数据诚实性，不能让读者误以为那是实时行情——在自己的门面上含糊其辞，是最廉价也最致命的自我否定。同时需说明真实源走 `apexfin collect --source yahoo` 进阶路径。

**附带收益**：`make demo-stale` 的实现因此变干净——陈旧不靠改数据库制造，而是切换到 `stale` fixture pack + 可注入 Clock。两者都是生产代码本就具备的能力（fixture 用于离线 demo，Clock 用于测试），不存在只为演示而生的 hack 分支，满足第十四章对架构师提出的「不要用改数据库这种脏手段」。

### 为什么 F6「故障注入演示」必须进 MVP（本 PRD 最重要的一条产品判断）

一个开源项目的差异化，必须在访客的**前 30 秒**内被理解，否则等于不存在。

APEXFIN 的差异化是「治理机制」，而治理机制在**一切正常时是隐形的**——正常跑一遍 demo，用户只会看到「哦，又一个能画图的量化项目」，与 solo-quant、Quant-Research-Lab 这类项目毫无区别，差异化归零。

**治理机制只有在失效发生时才可见。** 所以必须主动制造一次失效：

```bash
make demo         # 全链路跑通（fresh fixture pack），看板正常，数据健康度全绿
make demo-stale   # 切换 stale fixture pack → 新鲜度闸门 fail-loud → 管道中断 →
                  # 看板进入降级态：健康度区块转红，决策区显式标注"因数据陈旧未产出结论"
```

这两条命令的对比截图，就是 README 首屏，就是项目的全部说服力。**对比截图 >>> 一万字架构说明。**

同时这也直接回应了痛点 1 的调研原话——"detect the absence of expected behavior"——用户看到的不是一段承诺，是一次可复现的实证。

## 七、战略问题回答：APEXFIN 的真实价值主张是什么

team-lead 提出的问题：这个开源项目应该是「给别人用的工具」「展示架构能力的作品集」还是「可被 fork 的模板」？

### 结论：主定位是**可被 fork 的参考实现**；作品集价值是自然副产品；「给别人用的工具」必须明确放弃。

### 论证

**为什么不能是「工具」：**

工具意味着用户预期 API 稳定、issue 有人回、版本能升级。这个预期一旦建立，成本是刚性的——Airflow 1,791 个开放 issue、Dagster 2,611 个，这是「工具」定位的账单。而用户已经明说「目的不是让这个项目能运作起来」，即不打算长期投入。**在明确不打算长期维护的前提下宣称自己是工具，是对使用者的不诚实**——这与项目本身主打的「数据诚实性」价值观直接冲突，会成为最尴尬的自我打脸。

另有一个务实理由：工具赛道的对手是微软（Qlib，46.9k star）和 Apache 基金会（Airflow，46.4k star）。个人项目在功能完备度上无胜算。

**为什么不能主打「作品集」：**

作品集是**自我导向**的叙事（看我多厉害），而开源社区只对**读者导向**的叙事（这对你有什么用）买单。以作品集为主定位写出来的 README，会不自觉变成技术栈罗列和架构自夸，star 转化率极低。

但作品集价值不需要刻意追求——**如果代码本身足够好，架构能力会自动被读出来**。P2 用户画像（求职者）本身就是靠这个价值被吸引来的。所以：作品集是结果，不是目标。

**为什么必须是「可被 fork 的参考实现」：**

1. **它是唯一诚实的定位。** 参考实现天然不承诺 API 稳定，用户预期从一开始就是对的，不会有落空。
2. **它匹配 P1 用户的真实行为。** 孤狼工程师本来就不会原样用别人的采集器和策略，他们的行为就是「读 → 抄结构 → 接自己的源」。fork 是他们的默认动作，不是退而求其次。
3. **它有成功先例且成本可承受。** `machine-learning-for-trading`：20,228 star，2 个开放 issue。同等关注度下维护负担相差三个数量级。
4. **它把竞争维度从「功能多」换成「判断对」。** 微软能写出比你多十倍的功能，但微软不会写「我如何决定哪一步该被从每日管道里删掉」——那是个人研究者在真实约束下长出来的工程判断，是不可被大厂复制的内容。

### 这个结论对交付物的具体约束

| 交付物 | 因该定位产生的硬性要求 |
|--------|----------------------|
| README 首屏 | 第一屏是**两张对比截图**（正常态看板 / 数据陈旧降级态看板）+ 一条 `make demo` 命令。不是 badge 墙，不是 feature 列表，不是 `pip install`。**图注必须诚实标注截图数据来自内置 fixture 而非实时行情**，并指明真实源走 `apexfin collect --source yahoo` 进阶路径——在主张数据诚实性的项目门面上含糊其辞，是最廉价也最致命的自我否定。 |
| README 第二屏 | 「为什么这样设计」——三个痛点与三个治理机制的对应关系。这是本项目区别于所有竞品的内容，必须放在功能说明之前。 |
| README 显著位置 | 一段**明示的定位与边界声明**：这是参考实现，不承诺 API 稳定性，不接受功能请求，鼓励 fork 后按需改造。同时明确「不含任何真实交易策略，玩具动量仅用于演示链路连通」。 |
| Demo | 必须零配置、零 API key、离线可跑、单命令、60 秒内出结果。任何一条不满足，「5 分钟上手」指标即失败。 |
| 代码组织 | 治理层（质量门 / 新鲜度闸门 / manifest / 对账台账）必须是**低耦合、可独立抄走**的模块——因为这是用户真正会带走的东西。采集层与决策层则应刻意保持薄，明确标注为可替换。 |
| 仓库结构 | `docs/ARCHITECTURE.md` 必须有一张分层图。P2/P3 用户是靠这张图决定要不要深读的。 |
| 不要做 | 不要写 CONTRIBUTING.md 招募贡献者（招来了没人接，是负债）；不要建 Discord；不要发路线图承诺未来功能。 |

## 八、验收标准（Given / When / Then）

### AC-1 端到端链路连通（离线可复现）

- Given 一台仅安装 Python 3.11+ 的纯净机器，无任何 API key，无外部数据库，**且断开网络**
- When 执行 `git clone` 后运行 `make demo`
- Then 基于内置 fixture pack 完成采集 → bronze 落库 → silver 归一 → 质量门 → 新鲜度闸门 → 决策 → 看板渲染，并生成一个可直接双击打开的静态 HTML 文件；耗时目标见 NFR「上手时间」条目
- And 重复运行两次，产出的看板数据内容完全一致（确定性验证）

### AC-1b 真实源适配器可用（进阶路径）

- Given 有网络连接的环境
- When 执行 `apexfin collect --source yahoo`
- Then 真实拉取成功并正常入库，证明 `BaseCollector` 接口对接真实数据源成立
- And 此路径**不进入** `make demo` 默认链路，**不进入** CI 断言（因真实行情每日变化，与可复现性要求冲突）

### AC-2 质量门可阻断（核心差异化验收）

- Given 一次已完成的正常 demo 运行
- When 执行 `make demo-stale`（切换至 stale fixture pack，其最新记录业务时间超出新鲜度阈值）
- Then 新鲜度闸门以非零退出码中断管道，控制台输出明确指出「哪个数据源、滞后几个交易日、阈值是多少」，且决策层不产出任何结论
- And 该机制复用生产代码既有能力（fixture 切换 + 可注入 Clock），代码中不存在仅为演示而生的分支

### AC-3 降级态可见

- Given AC-2 触发的中断状态
- When 渲染看板（降级模式）
- Then 看板顶部数据健康度区块显示为异常状态（红色警示样式 + 文字说明），决策区显式呈现「因数据陈旧，本日未产出结论」，而**不是**渲染一个看起来正常的旧数字

### AC-4 采集器插件接口可扩展

- Given 一个第三方开发者只阅读 `BaseCollector` 抽象基类与其 docstring
- When 他新增一个自定义数据源类并在配置中注册
- Then 无需修改任何框架代码即可接入管道，且自动获得分层落库与质量检查能力

### AC-5 决策层策略可替换

- Given 内置的玩具动量参考实现
- When 开发者实现 `BaseStrategy` 的另一个子类并替换配置
- Then 管道正常运行且看板正确渲染新策略输出，框架不含任何对具体策略的硬编码假设

### AC-6 manifest 一致性校验

- Given `pipeline_manifest.yaml` 中声明的步骤集合
- When 运行 manifest 校验器
- Then 若存在「manifest 声明了但代码未注册」或「代码注册了但 manifest 未声明」的步骤，校验器以非零退出码报错并列出差异项

### AC-7 CI 可复现

- Given GitHub Actions 的纯净 ubuntu-latest 环境
- When 推送触发工作流
- Then `make demo` 完整通过，产物 HTML 作为 artifact 上传

### AC-8 隐私净化（一票否决项）

- Given 完整仓库
- When 全量扫描代码、配置、测试数据、git 历史
- Then 不存在任何 API key、券商凭据、持仓数据、Futu/IB 相关代码或配置、个人真实策略参数

## 九、边界条件

| 场景 | 期望行为 |
|------|---------|
| 空状态：首次运行、数据库为空 | 不报错崩溃；看板渲染空态引导，明确提示「尚无数据，请运行 `make demo`」 |
| 网络不可用 / 数据源超时 | 采集器按源隔离失败，单源失败不中断整条管道；失败记录写入运行日志与看板健康度区块 |
| 数据源返回空 DataFrame（yfinance 已知行为） | 视为采集失败而非成功，不得写入 bronze 层；这是对痛点 1 的直接防御 |
| 数据源限流（HTTP 429） | 指数退避重试，重试耗尽后标记该源失败并继续其余源 |
| 部分源新鲜、部分源陈旧 | 按源粒度判定；仅当 `risk_essential` 档位的源陈旧时才 fail-loud 中断，`display_only` 档位陈旧仅降级展示 |
| 非交易日运行（周末 / 假期） | 新鲜度按**交易日**而非自然日计算，周一早晨检查上周五数据不应误报 |
| 重复运行同一天 | 幂等：按 `(source, symbol, event_time)` 去重，重跑不产生重复记录 |
| 数值异常（负价格、极端值） | 数值合理性检查捕获并标记，不静默写入 |
| 时间序列跳空 | 连续性检查识别断点，区分「交易日历导致的正常跳空」与「真实数据缺失」 |
| 磁盘写入失败 / SQLite 锁 | fail-loud，明确报错，不吞异常 |
| 看板渲染时数据不完整 | 渲染降级态而非崩溃；缺失区块显示占位说明（说明缺什么、为什么缺），不使用空洞占位文案 |
| 时区 | 全链路统一以 UTC 存储，展示层按配置时区转换；数据契约中显式声明时区字段 |

## 十一、数据埋点方案

**本节对标准模板做了刻意偏离，理由如下：**

标准 PRD 模板要求前端埋点采集用户行为。**本项目明确不做任何运行时遥测**：

1. 在开源开发者工具中植入埋点是社区公认的信任毁灭行为（参见 Homebrew、Gatsby、Next.js 历次 telemetry 争议）。
2. 本项目主打「数据诚实性」，自己偷偷采集用户数据会构成根本性的价值观自相矛盾。
3. 本地静态 HTML 看板无服务端，技术上也无处上报。

**替代方案：使用 GitHub 原生指标 + 可选的本地自观测。**

### A. 项目层面：GitHub 原生指标（零侵入，无需用户同意）

| 指标类别 | 具体指标 | 判读用途 |
|---------|---------|---------|
| 触达 | Traffic → Views / Unique visitors | README 曝光量 |
| 兴趣 | Stars 增长曲线、Watch | 首屏说服力是否成立 |
| **意图（最关键）** | **Forks 数 / Clones 数** | **验证「可被 fork 的参考实现」定位是否成立——fork 数占 star 数比例若显著高于同类项目，说明定位命中** |
| 深度参与 | Issues / Discussions / 引用本项目的外部博客 | P3 教学者是否被吸引 |
| 流量来源 | Traffic → Referring sites | 判断传播杠杆在哪（HN / Reddit / 知乎 / 博客） |

**核心判读指标：fork / star 比值。** 普通工具类项目该比值通常在 0.1–0.2（多数人只 star 不 fork）；参考实现/模板类项目应显著更高。若本项目上线三个月后该比值低于 0.15，说明定位表述失败——用户把它当工具收藏而非当模板取用，需要改写 README。

### B. 系统层面：管道自观测（面向用户自己，不上报）

框架内建的运行时记录，**全部写入本地 SQLite，仅供用户自己在看板上查看**：

| 事件 | 记录内容 | 用途 |
|------|---------|------|
| `pipeline_run_started` | run_id, timestamp, 步骤总数 | 运行历史 |
| `step_completed` | run_id, step_name, tier, 耗时, 状态 | 定位慢步骤，为 tier 瘦身提供数据依据 |
| `quality_check_result` | run_id, 检查类型, source, symbol, 通过/失败, 详情 | 质量趋势 |
| `freshness_gate_triggered` | run_id, source, 滞后交易日数, 阈值 | 数据源可靠性历史，判断哪个源该换 |
| `decision_recorded` | run_id, 观点, 理由, 到期日 | 供 F11 对账台账消费 |

事件命名规范：`{对象}_{动作}`；统一附带 `run_id` 与 `timestamp`；**不采集任何用户身份、IP、机器指纹**。

## 十三、Out of Scope（明确不做）

| 不做 | 理由 |
|------|------|
| 实盘交易 / 券商 API 对接 | 超出「数据工程参考架构」边界；Futu/IB 相关代码为用户私有资产，必须全部剔除 |
| 回测引擎 | 赛道饱和且已有更好实现；README 中直接推荐 vectorbt / nautilus_trader |
| 真实 alpha 因子 / 用户真实策略 | 违反「抽框架不抽 alpha」核心原则 |
| 用户持仓、私有 API key、付费数据源 | 隐私红线；同时破坏零配置原则 |
| 分钟级 / tick 级数据 | 免费源不支持；会引入存储与性能复杂度，破坏「5 分钟上手」 |
| PostgreSQL / 云数据库 | SQLite 零配置是核心指标的前提 |
| Web 服务 / 登录 / 多租户 / RBAC | 本项目是单机工具，无服务端 |
| PyQt6 桌面客户端 | 前端已定为静态 HTML |
| 真实 LLM 调用与 API key 管理 | 破坏零配置；仅交付 prompt 契约层与确定性 mock |
| 中文以外的界面多语言切换 | 预留 i18n 接口即可，实现多语言无 ROI |
| Docker Compose 多服务编排 | 与「零外部服务」定位冲突；可提供单一 Dockerfile 作为可选项 |
| CONTRIBUTING.md / Discord / 公开路线图 | 与「不承诺长期维护」的诚实定位冲突，招募了贡献者却无人响应是更大的负债 |

## 十四、给下游角色的输入摘要

### 给架构师

- 治理层（质量门 / 新鲜度闸门 / manifest 校验 / 对账台账）必须**低耦合、可被单独抄走**——这是用户真正带走的东西，也是本项目全部差异化所在。采集层与决策层刻意保持薄且可替换。
- 新鲜度判定必须基于**业务时间 + 交易日历**，而非写入时间。这是相对 dbt `source freshness` 的关键差异点，不能做成时间戳比较了事。
- fail-loud 必须是**真中断**（非零退出码 + 阻止决策层产出），不能降级成打印警告。
- 依赖预算：核心运行时顶层依赖 ≤ 10；禁止引入需要独立进程的服务。
- 图标方案需锁定一个统一 SVG 图标库，禁 emoji（含 CLI 输出，用 `[PASS]` / `[FAIL]` / `[DEGRADED]` 文字前缀）。
- `make demo-stale` 的故障注入机制需要在架构层预留干净的注入点，不要用改数据库这种脏手段做成 hack。

### 给设计师

- 看板核心信息层级：**数据健康度区块必须在最顶部**，优先级高于任何行情图表。这是本项目的差异化所在，视觉上必须最先被看到。
- 必须设计两个状态：**正常态**与**数据陈旧降级态**。这两张图的对比就是 README 首屏，是项目最重要的视觉资产。
- 降级态设计要求：状态**不得仅靠颜色区分**（WCAG 2.1 AA + 色盲可辨），需同时有文字标签与图标形状差异。
- 风格基线：`saas-b2b.md` 的数据密集风 / 极简瑞士风，Slate–Indigo 系，克制专业。禁止紫色到粉色渐变。
- 空状态与错误态文案必须说明「具体发生了什么 + 用户该做什么」，禁止空洞占位。
- 交付物需包含可直接用于 README 首屏的截图规格建议。
