# ADR-005: 「抽框架不抽 alpha」的切割边界

## Status

Accepted (2026-08-02) — 高见远

## Background

APEXFIN 从私有系统 APEXDATA 抽取（`scripts/` 26 个 py + `scripts/pipeline/` 187 个 py，共 213 个，实测于 2026-08-02）。用户要求「抽框架不抽 alpha」，PRD 十三把「真实 alpha 因子 / 用户真实策略」列为 Out of Scope，AC-8 把隐私净化列为一票否决项。

难点不在「要不要删」，而在**边界画在哪里**。画太松会泄露真实策略；画太紧会把项目掏成空壳——一个只有抽象基类没有可运行实现的仓库，读者三十秒就会关掉。

## Decision

采用**三问判定规则**，逐文件过筛，判定结果与完整清单见 `docs/ALPHA_BOUNDARY.md`。

- **Q1 泄露问**：含或引用密钥、券商连接、持仓、账户、付费源凭据 -> DELETE（无例外）
- **Q2 alpha 问**：编码了「怎么赚钱」的判断（阈值、权重、因子公式、择时规则、实盘调优参数）
  - 可被通用抽象替代 -> SKELETONIZE
  - 本身就是 alpha 主体、抽象后只剩空壳 -> DELETE
- **Q3 骨架问**：表达「数据工程该怎么组织」的通用工程判断，脱离本人标的与策略后仍成立 -> KEEP，否则 DELETE

核心原则一句话：**保留「纪律」，丢弃「判断」。** 质量门怎么设计是纪律，阈值定多少是判断；管道怎么排序是纪律，排哪些步骤是判断。所有「判断」外置到 YAML 配置，代码内零魔数。

两条防止画过紧的补充规则：

1. **每个抽象必须配一个可运行的玩具实现。** 只有 `BaseStrategy` 没有 `ToyMomentum`，读者无法验证接口是否真的成立。玩具实现必须重写而非改写（不从原实现删参数，避免残留调优痕迹），且文件头显式声明 demonstration only。
2. **抽象后只剩空壳的不留位置。** 例如 `compute_alpha158.py` 的全部价值在 158 个因子定义上，抽成 `BaseFactor` 后骨架毫无信息量。给空壳留位置是伪装成架构的噪音，直接 DELETE。

骨架化的验收标准（可机器验证）：**把玩具实现整个删掉，框架仍能跑通，决策区显示 `no_call`。** 删掉后框架就崩，说明抽象没做干净，骨架里还粘着 alpha。

规模结果：213 个 py 文件切到约 60 个（削减 72%），27 个采集器切到 3 个，98 个管道步骤切到约 10 个，2 库 30+ 表切到 1 库 9 表。

## Consequences

正面：
- 边界可审计：每个文件的去留都能追溯到具体判定问，而不是「感觉不该放」。
- 价值密度集中在治理层——这正是 P1 用户会带走的部分（PRD 二·关键洞察）。
- 「删掉玩具仍可跑」这条验收标准把抽象质量变成了可测试的属性，而不是主观评价。

负面：
- 抽 alpha 后决策层的说服力显著下降。读者可能觉得「策略这么弱」。缓解：README 显式声明这是刻意的，并直接推荐 vectorbt / nautilus_trader 给需要真实策略的人——诚实边界本身就是本项目的价值主张之一。
- 人工复核不可省略。正则扫描只能拦住模式化泄露，prompt 角色卡里的个人偏好、符号清单里的关注标的池都需要人眼过（清单见 `ALPHA_BOUNDARY.md` 六）。
- 部分被删的模块（回测、校准、证伪）其实有通用价值，但落在 MVP 之外。记录在此，未来若要补，走新 ADR。

## 强制的独立行动项

APEXDATA 的 `scripts/pipeline/fetch_fred.py:22` 与 `fetch_fred_regional.py:23` 硬编码了同一个真实 FRED API key。**该 key 必须吊销并重新签发**——「APEXFIN 没带过去」不等于已解决，它已明文存在于私有仓库中。APEXFIN 采用全新 `git init`，不迁移 APEXDATA 的 git 历史。
