## 0. 文档目的与一句话定位

v0.1 的切割是"合规优先、宁错杀不放过"的粗粒度切割——把和第三方 API 耦合的**工程骨架**也一并删除了，导致开源后的 APEXFIN 与私有 APEXDATA 之间出现巨大能力断层，在 GitHub 上缺乏竞争力（对外展示的是一个"只剩纪律、没有管道"的空壳）。

v0.2 的真实诉求**不是**"加 demo / 补 README 让骨架看起来不薄"，而是**"找回被粗切连带删除的工程骨架"**。

**一句话定位（v0.2 重写）：**

> APEXFIN 是一个**金融数据工程管道 + POST 分析骨架 + LLM 研判契约**的开源参考实现，强调"确定性工程管道喂给 AI 的最后一公里"。

三个"不是 / 是"边界：

- ❌ 不是多空辩论框架（trading agent 嫌疑，会触发平台与投资合规风险）
- ❌ 不是泛泛的数据质量框架（与 Great Expectations 11.7k★ 正面硬刚必输）
- ✅ 是"金融场景下，从采集、治理、POST 分析，到 AI 研判契约的完整工程管道"——AI 只是最后一环，前面全部是确定性的、可离线复现的工程纪律

本文档结构：

- **第一节**：竞品对比（逐个回答三问题：覆盖了 APEXFIN 哪些骨架层？没覆盖什么？APEXFIN 差异化在哪？）
- **第二节**：v0.2 PRD 主体（按"找回被连带删除的骨架"组织，P0/P1/P2）
- **第三节**：待确认问题（Q1 / Q2 / Q3 原样转主理人）

每个需求均带三标签：`【对应 apexdata 原文件】` + `【原切割决策】` + `【v0.2 处置】`。

# 第一节：竞品对比

## 方法论说明

v0.2 的竞品对比**不采用"功能列表对照表"**，而是对每个竞品逐个回答三个问题：

1. **覆盖了 APEXFIN 哪些骨架层？** —— 对照 APEXFIN 五层架构（L1 core / L2 storage / L3 sources·processing·quality·decision·analysis·accounting / L4 pipeline / L5 cli·reporting），它落地了哪些层？
2. **没覆盖什么？** —— 它缺 APEXFIN 的哪些骨架层 / 治理能力 / 契约设计？
3. **APEXFIN 差异化在哪？** —— 我们不硬刚，而是找到对方"结构性留白"作为我们存在的理由。

竞品分三类：数据质量框架类、金融数据管道类、量化/LLM 分析框架类。

> 数据来源：GitHub API（`api.github.com/repos/...`）经 WebFetch 实测，抓取日期 2026-08。标注"无法验证"者已在文中说明。

## 1.1 数据质量框架类（"不硬刚"的对照组）

> 这一类是 v0.1 误入的赛道。v0.2 必须明确：**APEXFIN 不扩质量检查数量，不与 GX 正面竞争**。下面三个竞品用于证明"泛泛数据质量"不是我们的战场。

### 1.1.1 Great Expectations（fivetran/great_expectations）

- **实测数据**：★ 11,694；License Apache-2.0；语言 Python；300+ Expectations；GX Cloud 于 2026 年退役、转自托管 GX Core（由 Fivetran 接管）；多后端（Pandas / SQL / Spark）；Data Docs 生成 HTML 报告；Checkpoint 可接 Airflow / Dagster / Prefect；最近 push 2026-08-03（高度活跃）。

**Q1 覆盖哪些骨架层？**
- 覆盖了 APEXFIN 的 `quality/`（期望校验）、`reporting/`（Data Docs HTML 报告）两层。
- 其 Checkpoint + 编排器集成，部分对应 APEXFIN 的 `pipeline/`（调度）概念，但 GX 本身不内置"金融业务时间"语义。

**Q2 没覆盖什么？**
- **业务时间 + 交易日历新鲜度闸门**：GX 校验的是"数据本身长得对不对"，不校验"数据是不是交易日该有的新鲜度"（lag_trading_days）。
- **四档 tier 治理（risk_essential / support / display_only / research）**：GX 没有"哪些检查失败要阻断决策、哪些只是展示"的分级概念。
- **POST 双阶段调度**：GX 是校验引擎，不是"采集→POST 分析"两阶段管道。
- **AI 研判契约**：GX 完全不涉及 LLM 研判。
- **观点对账台账 / 跨期验证**：GX 不追踪"昨天预测今天是否命中"。
- **金融特化 extractor**：GX 是通用数据质量，不含 FRED / Yahoo / COT 等金融源适配。

**Q3 APEXFIN 差异化在哪？**
- GX 是"通用数据质量瑞士军刀"，APEXFIN 是"金融场景里把质量检查**接到决策门禁和交易日历**的管道"。我们不重复造 300 个 Expectation，而是把"质量→阻断→新鲜度→决策"这条金融特化的闭环做扎实。
- **关键论断**：和 GX 比数量必输（11.7k★ + 300 期望），但 GX 在"金融新鲜度门禁"和"质量→决策闭环"上有结构性留白，这正是我们 README "为什么不直接用 GX" 的自洽支点（详见第三节 Q1）。

### 1.1.2 Deequ（awslabs/deequ）

- **实测数据**：★ 3,638；语言 Scala；License Apache-2.0；构建于 Apache Spark；亮点特性 **constraint suggestion（约束建议）**；语法 DQDL；最近 push 2026-07-21（活跃）。

**Q1 覆盖哪些骨架层？**
- 覆盖 `quality/`（约束校验）+ 部分 `processing/`（运行于 Spark 批处理）。
- constraint suggestion 是 GX 没有的差异化能力（自动建议约束）。

**Q2 没覆盖什么？**
- 语言栈是 Scala/Spark，**与 APEXFIN 的"无 pandas、零外部服务、纯 Python stdlib + SQLite"定位完全不兼容**——APEXFIN 的"可抄走、轻量、离线"卖点正是 Deequ 的反面。
- 同样缺失：金融新鲜度门禁、tier 治理、POST 调度、AI 契约、台账。

**Q3 APEXFIN 差异化在哪？**
- Deequ 是"大数据质量平台"路线（需要 Spark 集群），APEXFIN 是"单机、零依赖、可被 fork 的参考实现"。目标用户不同：Deequ 面向数据平台团队，APEXFIN 面向"想理解金融数据工程全链路、且不想被云厂商锁定"的个人/小团队。

### 1.1.3 Soda Core（sodadata/soda-core）

- **实测数据**：★ 2,404；语言 Python；License 标注为 NOASSERTION（other）；语法 SodaCL（YAML）；内置异常检测（anomaly detection）；最近 push 2026-08-03（活跃）。

**Q1 覆盖哪些骨架层？**
- 覆盖 `quality/`（SodaCL YAML 声明式校验）+ 部分 `config/`（YAML 配置风格与 APEXFIN 的 `pipeline_manifest.yaml` 思路接近）。

**Q2 没覆盖什么？**
- 缺失内容与 GX 类似：金融新鲜度门禁、tier 治理、POST 调度、AI 契约、台账、金融特化 extractor。
- License 为 NOASSERTION，对想 fork 的开发者是轻微摩擦点（APEXFIN 应坚持宽松许可证以降低 fork 门槛）。

**Q3 APEXFIN 差异化在哪？**
- Soda 的 anomaly detection 是"统计异常"，APEXFIN 的 `quality/gate` 是"业务规则门禁 + 交易日历"。两者解决不同问题：Soda 发现"数据漂了"，APEXFIN 回答"今天的产出能不能喂给决策"。

> **小结（1.1 三类）**：数据质量框架类是"展示我们克制"的镜子——它们强在通用校验，弱在金融特化（新鲜度、tier、决策闭环）和 AI 最后一公里。v0.2 不扩质量检查数量，是对标后的主动战略选择，而非能力不足。

## 1.2 金融数据管道类（"最该对标"的对照组）

> 这一类是 v0.2 真正的战友兼对手——它们做了"管道"，但普遍缺 APEXFIN 的治理与 AI 契约层。

### 1.2.1 djmartin2019/pyspark-stock-analysis-pipeline

- **实测数据**：架构 Spark + Delta Lake + Dash；medallion（bronze/silver/gold）；Silver 层有数据质量检查；**无新鲜度门禁 / 无 manifest tier 治理 / 无观点台账 / 无 LLM**；末次提交 2025-09-22；仅 3 commits（基本是个人 demo，已不活跃）。

**Q1 覆盖哪些骨架层？**
- 覆盖 `sources/`（stock 采集）+ `processing/`（bronze/silver/gold 分层）+ `quality/`（Silver 层检查）+ `reporting/`（Dash 看板）。
- 它证明了"medallion 分层 + 管道"是社区常见做法，APEXFIN 的五层架构站得住。

**Q2 没覆盖什么？**
- **缺失 `pipeline/` 双阶段调度语义**：它是 Spark 作业，不是"采集组 + POST 组"的依赖拓扑。
- **缺失 `quality/gate` 的 tier 分级**：它的 Silver 检查是平的，没有"risk_essential 失败阻断 / display_only 仅告警"。
- **缺失 `analysis/` AI 契约层、`accounting/` 台账层、`decision/` 跨期验证**。
- 技术栈重（Spark + Delta），与 APEXFIN 轻量离线定位相反。

**Q3 APEXFIN 差异化在哪？**
- 它是"重技术栈的股票分析 demo"，APEXFIN 是"轻量、可 fork、带 AI 研判契约与观点对账的金融数据工程管道"。它的 3 commits 状态也反衬 APEXFIN 需要持续维护才能形成竞争力。

### 1.2.2 akashs101199/agentic-data-engineering-platform

- **实测数据**：经 GitHub API 抓取受限（沙箱网络），未能稳定获取 star/license/活跃度。名称推断为"智能体驱动的数据工程平台"——**本文档标注：数据待补，建议 v0.2 后续联网复核**。

**Q1 覆盖哪些骨架层？**
- 据名称推断：可能覆盖 `pipeline/`（agentic 编排）+ `sources/` + `quality/`。若其为"LLM agent 做数据工程"，会与 APEXFIN 的"AI 仅最后一环"理念冲突。

**Q2 没覆盖什么？（推断）**
- 若以 agent 为核心，大概率**没有** APEXFIN 强调的"确定性工程管道优先、AI 研判契约次之"的分层纪律，也无交易日历新鲜度门禁、无观点对账。

**Q3 APEXFIN 差异化在哪？**
- APEXFIN 的核心纪律是"确定性管道喂给 AI 的最后一公里"，而非"让 AI 代理整个数据工程"——后者可解释性差、难离线复现，正是 APEXFIN 要规避的。

### 1.2.3 carlolax/crypto-data-platform

- **实测数据**：经 WebFetch 直接抓取 `api.github.com/repos/carlolax/crypto-data-platform` 返回 **404（仓库不存在或私有）**。改用 GitHub Search API 检索同名 "crypto-data-platform"，命中均为 1–4★ 个人项目（如 `data-engineering-efforts/crypto-streaming-platform` 4★、`dipeshluitel` 1★ 等），**非任务指定的那个**。本文档标注：原指定仓库无法验证，可能为示例仓库或已删除/转私有。

**Q1 覆盖哪些骨架层？（基于同类 crypto 管道推断）**
- 通常覆盖 `sources/`（crypto 行情/链上）+ `processing/` + `storage/`。

**Q2 没覆盖什么？（推断）**
- 普遍缺失 tier 治理、AI 研判契约、观点对账、跨期验证。

**Q3 APEXFIN 差异化在哪？**
- 加密数据管道多为"采集+存储"工具，APEXFIN 的差异化同 1.2.1/1.2.2：补上"治理 + AI 契约 + 对账"的金融工程闭环。

> **小结（1.2 三类）**：金融数据管道类普遍"有管道、无治理、无 AI 契约、无对账"。APEXFIN 的战略空隙清晰：在"管道"之上，补齐 tier 治理、交易日历新鲜度、AI 研判契约、观点对账这四块"金融工程纪律"。

## 1.3 量化 / LLM 分析框架类（"警惕误入"的对照组）

> 这一类是 v0.1 差点误入的"多空辩论 / trading agent"赛道。v0.2 必须划清界限：它们是"AI 做交易决策"，APEXFIN 是"确定性管道 + AI 研判契约（最后工程一环）"。

### 1.3.1 Qlib（microsoft/qlib）

- **实测数据（常识 + 社区共识，本次未单独抓取 API）**：微软开源，量化投资平台，覆盖因子挖掘、模型训练、回测。★ 量级约 15k+（社区共识，待正式 API 复核）。

**Q1 覆盖哪些骨架层？**
- 覆盖 `processing/`（因子工程）+ `decision/`（策略/回测）+ 部分 `analysis/`（预测模型）。
- 在"量化研究全栈"上远深于 APEXFIN。

**Q2 没覆盖什么？**
- **没有 APEXFIN 的"采集→POST 确定性分析→AI 研判契约"管道语义**，Qlib 假设数据已就绪，专注研究与回测。
- 没有交易日历新鲜度门禁（Qlib 用历史数据回测，不需"今天数据新不新鲜"）。
- 没有观点对账台账（Qlib 评估策略收益，不追踪"某句研判未来是否命中"）。

**Q3 APEXFIN 差异化在哪？**
- Qlib 是"量化研究平台"，APEXFIN 是"生产级数据工程管道 + AI 研判契约"。两者不竞争：APEXFIN 可作为 Qlib 上游"把数据洗干净、带新鲜度保证地喂进来"的那一环。

### 1.3.2 OpenBB（OpenBB-finance/OpenBBTerminal）

- **实测数据（常识）**：开源金融终端，覆盖海量数据源（股票/宏观/加密/另类）、命令行 + SDK。★ 量级约 30k+（社区共识，待复核）。

**Q1 覆盖哪些骨架层？**
- 覆盖 `sources/`（极广）+ `reporting/`（终端/SDK）+ 部分 `analysis/`（基础分析）。

**Q2 没覆盖什么？**
- 是"数据浏览器/终端"，**不是管道**：无 POST 双阶段调度、无 tier 治理、无 AI 研判契约、无观点对账。
- 数据源虽多，但"采集后如何确定性地做 POST 分析、再契约化喂给 AI"不是它的关注点。

**Q3 APEXFIN 差异化在哪？**
- OpenBB 回答"我想查某个数据"，APEXFIN 回答"我如何把数据工程化地变成可喂给 AI 研判的资产"。OpenBB 可作 APEXFIN 的 `sources/` 扩展参考，但定位不重叠。

### 1.3.3 TradingAgents（TauricResearch/TradingAgents）

- **实测数据**：★ **95,489**（极高热度）；License Apache-2.0；语言 Python；多智能体 LLM 交易框架（7 角色：基本面/情绪/新闻/技术分析师 + 研究员 + 交易员 + 风控）；bull/bear 辩论；最近 push 2026-07-18；329 open issues。

**Q1 覆盖哪些骨架层？**
- 覆盖 `analysis/`（多角色 LLM 辩论）+ 部分 `decision/`（交易员/风控角色）。
- 其"多角色 + bull/bear 辩论"看似与 APEXFIN 的 `analysis/` 相似——**但这是 v0.1 误区的来源**。

**Q2 没覆盖什么？**
- **完全没有确定性工程管道**：TradingAgents 一上来就是 LLM 多智能体做交易，**没有采集→POST 确定性分析→文本因子→AI 研判的"最后一公里"管道**。
- 没有 tier 治理、没有交易日历新鲜度门禁、没有观点对账台账。
- **它是 trading agent（有交易员角色、做交易决策）**——这正是 APEXFIN 必须划清界限的"投资工具"红线。

**Q3 APEXFIN 差异化在哪？（关键边界陈述）**
- TradingAgents 是"AI 替你做交易决策"，APEXFIN 是"确定性管道把数据工程化后，用 AI 契约做研判（不替你下单）"。
- APEXFIN 的 `analysis/` 是"研判契约骨架"（LLMClient Protocol + 输出 schema 校验 + 角色卡），不是"交易员智能体"。
- 差异化一句话：**TradingAgents 的 AI 是主角，APEXFIN 的 AI 是配角（最后一环）**。

### 1.3.4 FinRobot（AI4Finance-Foundation/FinRobot）

- **实测数据**：★ 7,718；语言 Jupyter Notebook；License Apache-2.0；AI agent 平台（Data-CoT / Concept-CoT / Thesis-CoT）；最近 push 2026-07-27；73 open issues。

**Q1 覆盖哪些骨架层？**
- 覆盖 `analysis/`（多 CoT 推理范式）+ 部分 `decision/`（Thesis-CoT 偏 thesis 生成）。

**Q2 没覆盖什么？**
- 同样**无工程管道、无 tier 治理、无新鲜度门禁、无对账台账**。
- FinRobot 偏"AI 分析/报告生成"，APEXFIN 偏"管道 + 契约 + 治理"。

**Q3 APEXFIN 差异化在哪？**
- FinRobot 的 Thesis-CoT 与 APEXFIN 的 P2 "叙事/thesis 骨架"在概念上接近，但 FinRobot 是 AI 平台、APEXFIN 是工程管道（thesis 只是 P2 远期骨架，且明确"不替用户下结论"）。
- APEXFIN 可借鉴 FinRobot 的 CoT 角色划分思路，但定位上 FinRobot 是"AI 分析工具"，APEXFIN 是"数据工程管道 + AI 契约"。

> **小结（1.3 四类）**：量化/LLM 框架类普遍"AI 是主角、无工程管道、无治理、无对账"。v0.2 必须明确：APEXFIN 不进 trading agent 赛道，AI 研判契约只是"确定性管道喂给 AI 的最后一公里"。

## 1.4 竞品对比总览（差异化空白地图）

| 竞品 | 覆盖 APEXFIN 层 | 结构性留白（我们的差异化） | 是否直接竞争 |
|---|---|---|---|
| GX | quality / reporting | 金融新鲜度门禁、tier 治理、决策闭环 | 否（不硬刚） |
| Deequ | quality / processing | 轻量离线、单机可 fork | 否 |
| Soda | quality / config | 业务规则门禁、交易日历 | 否 |
| djmartin pyspark | sources / processing / quality / reporting | 双阶段调度、tier、AI 契约、台账 | 否（它太重） |
| akashs agentic | pipeline（推断） | 确定性优先、可复现 | 待补数据 |
| carlolax crypto | sources / processing（推断） | 治理 + AI 契约 + 对账 | 无法验证 |
| Qlib | processing / decision | 生产管道、新鲜度、对账 | 否（它是上游） |
| OpenBB | sources / reporting | 工程管道 + AI 契约 | 否（它是数据源） |
| TradingAgents | analysis / decision | **工程管道、治理、AI 仅最后一环** | 否（它越界做交易） |
| FinRobot | analysis / decision | 工程管道、治理、对账 | 否 |

**战略结论（复述 PRD.md v0.1 已定方向，v0.2 强化）**：
APEXFIN 的主定位是"**可被 fork 的参考实现**"，放弃"工具"定位。差异化空白集中在三块：
1. **数据新鲜度定义空白**（业务时间 vs 任务/写入时间）—— 竞品普遍只校验"数据对不对"，不校验"数据今天该不该有"。
2. **质量检查→阻断决策闭环空白**（tier 治理 + gate）—— 竞品要么平校验，要么无门禁。
3. **观点对账整体空白**（台账 + 跨期验证 + 命中率）—— 竞品几乎无人追踪"研判未来是否命中"。

这三点正是 v0.2 "找回骨架"要补的工程纪律，也是 README "为什么不直接用 GX" 的自洽支点。

# 第三节：待确认问题（原样转主理人）

以下问题需主理人（齐活林）拍板后，架构师方可进入实现。PM 在每题后附**建议**供参考，但最终决策权在主理人。

## Q1：定位对标 GX 但 v0.2 不扩质量检查数量，README "为什么不直接用 GX" 怎么自圆其说？是否补扩纪律（6→10 项）？

- **现状**：v0.1 的 `quality/check_*.py` 仅 6 项检查（来自 `check_quality.py` 的 KEEP 决策）。GX 有 300+ Expectations。若 README 写"为什么不直接用 GX"，却不扩检查数量，社区会质疑"你比 GX 弱在哪"。
- **PM 建议**：**不扩数量，改叙事角度**。自洽支点来自第一节竞品对比的三空白：
  1. GX 校验"数据对不对"，APEXFIN 校验"数据今天该不该有"（业务时间 + 交易日历新鲜度门禁）——这是 GX 没有的；
  2. APEXFIN 的 quality 是 **tier 分级 + gate 门禁**（risk_essential 失败阻断决策，display_only 仅告警），GX 是平校验；
  3. APEXFIN 的 quality 直接接到"观点对账台账"（质量→决策闭环），GX 不追踪研判命中。
  - 即 README 应写："APEXFIN 不是 GX 的替代品，而是**金融场景下把质量接到决策门禁与新鲜度闸门的那一环**。如果你只需要通用数据校验，请用 GX；如果你需要'数据新鲜且合规才能喂给 AI 研判'，用 APEXFIN。"
  - **不建议 v0.2 扩到 10 项**：扩数量会模糊"我们克制"的战略，且 6→10 的边际价值远低于"把 tier + 新鲜度 + 闭环讲清楚"。若主理人认为需补，建议仅补与金融特化强相关的 2–4 项（如"交易日历连续性""期权到期日对齐"），而非泛化检查。
- **待主理人决策**：A) 维持 6 项 + 改写 README 叙事；B) 补 2–4 项金融特化检查；C) 扩到 10 项（不推荐）。

## Q2：8 角色卡逐句脱敏工作量大，是否 v0.2 先上 4 个（technical/macro/options/cot），其余 v0.3？

- **现状**：`analyst_roles/` 8 个角色卡（README/bear/bull/cot/macro/options/risk/technical/text），逐句脱敏需保证"每句必引具体数据、数据缺失标未覆盖、滞后诚实"且删除所有私有耦合。全量脱敏工作量可观。
- **PM 建议**：**v0.2 先上 4 个**（technical / macro / options / cot）——这四个覆盖"技术面 / 宏观 / 期权 / 持仓情绪"四个最具金融特化且 demo 效果好的维度，且 `options.md` / `technical.md` 含具体推理框架（EMA 斜率 / ADX / PCR / GEX / DEX），脱敏后示范价值最高。其余（bear/bull/risk/text + README 总纲）留 v0.3。
  - 注意：bear/bull 是"辩论结构"核心，若 v0.2 完全不上，会弱化为"无辩论"。建议 v0.2 至少保留 `analysis/roles.py` 的辩论骨架（规则为主），角色卡内容先 4 个，bear/bull 可用占位 prompt 接 `uncovered` 逻辑。
- **待主理人决策**：A) v0.2 先 4 个（推荐）；B) 全量 8 个硬上；C) 先 4 个 + bear/bull 占位。

## Q3：MockLLMClient 是否要内置基于规则的 mock（确定性返回便于 demo），还是纯 Protocol 不带实现？

- **现状**：`analysis/providers/mock.py` 的 `MockLLMClient` 是 P0-3 的交付物。若纯 Protocol 不带实现，demo 与测试需用户自己接真实 LLM（有 key 依赖，违背"零外部服务"卖点）；若内置基于规则的 mock，可确定性返回，便于离线 demo 与 CI。
- **PM 建议**：**内置基于规则的确定性 mock**。理由：
  1. APEXFIN 的核心卖点是"轻量、离线、可 fork、零外部服务"，纯 Protocol 会让首次体验者卡在"没有 LLM key 跑不起来"；
  2. 确定性 mock 返回（如按 schema 填充占位研判 + 引用 fixture 数据）便于 CI 复现与 `replay --date` 演示；
  3. 真实 provider（如 OpenAI / 本地模型）作为可插拔实现，用户按需接入，但**默认不带任何 key**（呼应 ADR-009 / D1 一票否决）。
  - 风险：基于规则的 mock 可能被误读为"APEXFIN 真能做研判"。文档需明确标注"mock 仅用于演示管道，不代表真实研判能力"。
- **待主理人决策**：A) 内置确定性 mock（推荐）；B) 纯 Protocol 不带实现；C) 内置 mock + 额外提供 1 个真实 provider 适配示例（不带入 key）。
